# React 기반 공동 디자인 작업실

2026-09-11 고객 미팅 후 사용자 요구를 반영한다. 기존 파일 반입·HTML 검수 구현은 입력과 참고 검증으로 유지하며,
최종 납품·승인·배포 단위는 React 프로젝트와 그 프로젝트에서 실제 빌드한 정적 번들이다.

## 확정 요구

- 외부에서 전달받은 HTML·SVG·PNG/JPG 등 자산을 반입한다. Studio의 Figma 직접 접속은 요구하지 않는다.
- 컴포넌트의 기준은 실제 React 코드다. MD는 상품·업무·작업 가이드의 입력으로 사용할 수 있지만 컴포넌트 구현을 대신하지 않는다.
- 승인된 컴포넌트 패키지의 버전·소스 해시·타입·토큰을 실행마다 고정한다. AI는 화면 구성과 상태 로직을 생성한다.
- 생성 모드는 `creative`와 `guided`다. 전자는 가이드 안에서 새로운 UX를 만든다.
  후자는 기준안 1개와 선택한 2~5개 변형안, 총 3~6개를 만든다.
- 모든 안에 동일한 필수 업무 규칙과 컴포넌트 규격을 적용한다. 변형 가능한 배치·밀도·강조·정보 순서는 별도로 기록한다.
- 기획·디자인·개발은 상품/페이지별 공통 사이드바에서 가이드와 논의를 공유한다.
- 기획이 확정한 상품 가이드는 버전이 있는 온톨로지로 저장되며 UX 규칙과 안내 페이지 생성의 출처가 된다.
- 개발자는 승인된 페이지에서 실제 소스·빌드·테스트 결과와 연결된 feature branch·커밋을 확인한다.
- 실패·미판정·변경된 기준·다른 산출물 해시는 배포/커밋 승인으로 승격하지 않는다.

## 컴포넌트와 생성 코드

현재 저장소의 기존 Registry는 이름·props 메타데이터를 제공하지만, 기존 검증기의 `ui-stub.js`는 실제 제품 컴포넌트가 아니다.
새 경로는 별도의 실제 React 패키지 `@studio/approved-ui`를 사용한다.
고객 패키지의 경로·버전은 사용자에게 질의했으며, 지정 전에는 플랫폼 기본 패키지임을 명시한다.
플랫폼 패키지를 고객의 사내 승인 패키지로 표시하지 않는다.

패키지는 React 구현, CSS/토큰, 타입 선언, 코드 해시 manifest, 단위·브라우저 테스트를 포함한다.
생성 모델은 이 패키지의 소스를 수정하거나 대체할 수 없다. 생성 소스는 화면 조합·상태 전이 역할인 `src/App.tsx`에 한정한다.
프로젝트 설정·의존성 lockfile·빌드 스크립트·검수 코드는 신뢰된 템플릿에서 제공한다.

처음 제공할 실제 컴포넌트는 Screen, Stack, Grid, Inline, Panel, Text, Button, Input, Checkbox, Select,
RadioGroup, Alert, Stepper, Summary, AssetImage다. 외관은 패키지 토큰과 허용된 props로 결정한다.
임의 CSS/HTML 삽입, 승인되지 않은 UI import, 동적 코드 실행, 직접 DOM 변경으로 규격을 우회하는 생성 소스는 거부한다.
추가 컴포넌트나 토큰 변경은 패키지 변경·테스트·검토·새 버전 게시를 거친다.

## 실제 빌드와 검증

1. 고정된 컴포넌트/도구/의존성 해시와 선택한 자산을 확보한다.
2. 생성 TSX의 import·JSX·속성·위험한 실행 경로를 TypeScript AST로 검사한다.
3. 스텁 선언이 아닌 실제 컴포넌트 타입으로 TypeScript 검사와 production build를 실행한다.
4. 네트워크가 격리된 실행기에서 그 빌드 번들을 실제 React로 렌더링한다.
5. 승인된 규칙으로 입력·전이·값 전달·동의·조건·스타일·접근성을 시험한다.
6. 지정된 기준 이미지가 있으면 같은 화면 크기·상태에서 비교한다. 시작 화면 비교와 전체 상태 비교를 구분한다.
7. 실패 근거를 모델에 전달하되 컴포넌트 코드와 승인 기준은 바꾸지 않고 화면 소스만 수정한다.
8. 소스 프로젝트, 배포용 `dist`, 테스트, 증거, 파일 해시 manifest를 함께 보존한다.

빌드 중 임의 업로드의 package.json 스크립트·설정·플러그인을 실행하지 않는다.
도구와 의존성은 실행기 이미지에 고정해 설치하며 실행 중 외부 npm/폰트/이미지를 내려받지 않는다.
컴파일과 렌더링은 AWS 데이터 자격 증명이 없는 제한된 자식 프로세스에서 수행한다.
빌드가 통과해도 브라우저 검사가 실패하면 납품 가능 상태가 아니다.

## 기준안과 변형안

배치에는 반드시 기준안 하나가 있다. `variationCount`는 정수 2~5이며 각 변형은 독립된 실행·수정 이력을 갖는다.
하나의 안이 실패해도 다른 안의 상태를 덮어쓰지 않고 해당 안만 다시 시도할 수 있다.
기준안의 가이드 준수와 변형안의 허용 변경 범위를 같은 점수로 섞지 않는다.

기준 이미지와 동일해야 하는 영역·상태는 필수 시각 기준이다.
의도적으로 배치가 다른 변형안은 기준 이미지와의 차이를 보여주되 이를 픽셀 일치 통과로 표시하지 않는다.
해당 안의 필수 규칙과 코드 규격이 통과하고, 디자이너가 허용된 변형 범위를 확인해야 선택·승인할 수 있다.
`creative`도 동일한 필수 기준을 사용하며 업무 조건을 새로 추정한 경우에는 확정 전 기준으로 사용하지 않는다.

## 공동 작업과 온톨로지

공동 작업은 프로젝트 단위이며 멤버 역할은 owner/planner/designer/developer다.
기존 개인 반입 자료는 자동 공개하지 않는다. 프로젝트에 반입하거나 명시적으로 복사한 자료만 멤버가 함께 사용한다.
프로젝트 ID만 아는 사용자는 데이터에 접근할 수 없으며, 모든 API에서 실제 멤버 권한을 확인한다.

기획 사이드바는 상품명·상품 설명·조건·절차·필수 안내와 논의 기록을 편집한다.
초안 저장과 기준 확정을 구분한다. 확정 시 불변 가이드 revision과 그 출처 텍스트, typed nodes/edges를 저장한다.
온톨로지는 Product, Condition, PolicyRule, Procedure, ScreenMeta와 관계로 구성되며 프로젝트 권한 안에서 조회한다.
화면 생성은 이 온톨로지를 읽어 필요한 UX 경로와 안내 페이지를 제안하고, 출처 노드/가이드 revision을 규칙에 연결한다.
메모리 내 표시만으로 온톨로지 저장 성공을 주장하지 않는다.

논의는 상품/가이드 revision/페이지/라운드에 연결하며 작성자·시각·편집 이력을 보존한다.
가이드가 바뀌면 관련 페이지를 영향 목록에 표시하고 재검증이 필요한 것으로 처리한다.
기존 승인 기록은 과거 버전의 사실로 보존하지만 최신 기준의 배포 승인으로 재사용하지 않는다.

## 승인·S3·Git

승인은 선택한 React 소스, 컴포넌트 lock, 온톨로지/규칙 revision, 실제 dist, 검수 보고서의 동일 해시에 귀속된다.
승인 후 release 생성은 같은 소스를 신뢰된 설정으로 다시 빌드·검증하고 동일 번들을 확인한다.
불일치하거나 기준이 변경되면 새 승인이 필요하다.

release는 비공개 S3에 소스 ZIP, dist ZIP/파일, 테스트·manifest·검수 보고서를 보관한다.
고객 배포 대상이 설정되지 않은 상태에서 기존 공개 웹 버킷으로 고객 산출물을 게시하지 않는다.

Git 대상은 관리자가 등록한 연결에서 선택한다. 사용자에게 실제 대상 저장소를 질의했으며,
연결 전에는 소스 프로젝트 다운로드는 가능하지만 원격 커밋 성공이나 커밋 URL을 만들지 않는다.
Git 연결은 고정된 대상·자격 증명 참조·허용 경로·기준 브랜치를 사용하며 생성 모델이 URL이나 권한을 지정하지 못한다.
feature branch는 기준 SHA에서 생성하고, 승인된 release 소스만 커밋한다. main 직접 쓰기·강제 push는 제공하지 않는다.
중복 요청은 동일 커밋을 반환하고, 충돌·외부 변경은 덮어쓰지 않는다.
개발자 사이드바에는 실제 branch/commit SHA/URL, 소스 파일, 빌드·테스트 결과와 승인자를 표시한다.

## 완료 증거

- 실제 React 컴포넌트로 만든 화면의 타입 검사·production build·브라우저 테스트 결과.
- 생성 모델이 컴포넌트 코드를 바꾸거나 규격을 우회할 때 거부하는 테스트.
- 두 생성 모드, 기준안 1개와 2/5개 변형안 경계, 부분 실패·선택·동일 기준 수정.
- 두 사용자 이상의 프로젝트 권한·논의·가이드 확정·온톨로지 조회·변경 영향 검증.
- 입력 금액 변경·미동의·범위 오류·뒤로가기·안내 페이지가 가이드와 일치하는 정상/실패 시험.
- 승인 후 같은 소스/컴포넌트/기준/dist 해시의 release, 다른 해시·변경된 기준의 거부.
- Git feature branch 생성·충돌·재시도와 실제 커밋 조회. 고객 원격 저장소 연결 여부는 별도로 명시.
- PR의 AI 검토에서 Critical/Major를 수정한 뒤 조건부 머지하고 실제 플랫폼 배포를 확인.
